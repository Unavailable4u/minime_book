MiniMate — Product & Build Guide

From coding agent to personal automation system on Linux

Version 1.0 · written 2026-10-02 · companion to minimake_guide.md (read that first; MiniMate reuses most of it)

Names: MiniMate (this product, formerly "miniU") and MiniMake (the coding agent, formerly "MiniCode"). Paths and commands use the new names (minimate, ~/.minimate/).

0. How to read this guide

What this is. A full specification of MiniMate: an always-available, automation-focused agent that acts for the user across their files, apps and accounts, on Linux first, powered by MiniMe's orchestration and premium models. It is built from the same research as the MiniMake guide plus a second pass on personal and "computer-use" agents: OpenClaw, Hermes Agent, Claude Cowork, ChatGPT Agent, Manus, Devin, Linux desktop-control tools, the 2026 MCP spec, ACP, Agent Skills, and the prompt-injection literature.

What this is not. It is not a plan to build an operating system. Section 10 explains what "agentic OS" can honestly mean and recommends a path that does not involve building a distribution until demand proves it.

1. Executive summary

MiniMate in one paragraph. A personal automation agent that lives where the user already is (terminal, messaging apps, the MiniMe web app, later voice), runs tasks on demand, on a schedule, and on triggers, uses the user's files and accounts through scoped connectors, remembers what matters, learns reusable skills, and asks for approval at the right moments through one inbox. The "brain" is MiniMe's backend with premium and cheap models routed by task; the "hands" are a local Linux agent, cloud sandboxes for untrusted or unattended work, and MCP connectors. It is MiniMake's engine with a different profile: broader tools, a scheduler, memory, channels, and a stricter security model because it acts without a developer watching.

The ten decisions this guide makes

  1. MiniMate is a profile on the MiniMake engine, not a second codebase [P]. Same loop, tool broker, permission engine, session log and metering, with different tools, prompts and surfaces (§4.4, §5.6).
  2. "A personal agent is a gateway problem, not a model problem." The OpenClaw lesson: queuing, channel normalization, memory, extensibility and security are where the work is [R:S21]. Build the gateway and runtime well; models are swappable.
  3. Automations are first-class objects with a trigger, a scope, a policy, a budget and an audit trail, not chat messages with a timer [P].
  4. Heartbeats must be cheap by design. A periodic wake-up is the biggest hidden cost; skip empty ticks without calling a model, pre-filter with scripts, and use the cheapest class (§6.4, §13.3).
  5. Security tiers and unattended policies come before features. Each capability gets a tier (T0–T5); unattended runs may only use pre-approved, narrowly scoped tiers; everything else queues for human approval [P].
  6. Break the lethal trifecta by construction where possible: automations that read untrusted content do not get write or egress tools, and automations with write tools do not read untrusted content, using split agents and sealed tool endpoints [R:S29].
  7. Credentials never reach the model or the sandbox. Vault plus proxy plus sealed endpoints, the pattern Anthropic documented for Managed Agents [R:S5].
  8. MCP first, native connectors second. Use the 2026-07-28 MCP spec's OAuth and tasks extension; wrap with your own permission stances per tool [R:S26, S23].
  9. Linux desktop control is a tiered ladder: APIs and CLI first, accessibility tree second, screenshots third, raw input last, and run risky or unattended desktop work in a headless virtual desktop, not on the user's real session [R:S24, S23].
  10. Do not build a distro. Ship a user-level service, a desktop integration, and optional images; consider an appliance later if users ask [P].

2.2 The market in 2026, briefly

  • Consumer and prosumer agents (ChatGPT Agent, Manus, Cowork) compete on convenience; they run in the vendor's cloud or a vendor-controlled VM [S33, S23].
  • Self-hosted always-on agents (OpenClaw, Hermes) compete on openness and channels; their weakness is security and operations [S21, S22].
  • Linux desktop control exists as open-source MCP servers but is rough and compositor-dependent [S24].
  • Gap for MiniMate: a managed product that is as capable as the self-hosted agents, as easy as the consumer ones, and safer than both, using premium models and orchestration you already operate. Linux users are underserved by vendor desktop agents (Cowork is macOS and Windows only [S23]).

2.3 Twelve lessons

  1. It is a gateway problem. OpenClaw's authors and analysts describe the hard part as connecting, queuing, remembering and extending, not the agent loop [S21].
  2. Proactivity is a cron job plus a checklist. The heartbeat pattern is simple and powerful, but the default of 30 minutes means 1,440 model calls a month per user if it is not gated [S21].
  3. Memory as files wins on trust. Plain Markdown (MEMORY.md, USER.md, dated notes) that the user can read and edit, indexed for search [S21, S22].
  4. Skills are the unit of reuse, and also the unit of attack. One analysis found 36% of marketplace skills had flaws and 283 leaked credentials; a security team built a malicious skill to prove the trust model could be abused [S21].
  5. Agents that learn their own skills are the next step (Hermes), but self-written procedures need review, versioning and tests, or they entrench mistakes [S22, S17].
  6. A split design limits blast radius. Cowork runs the loop and file access natively but puts code execution in a VM; Anthropic notes the VM caps what generated code can do, while folder permissions are what constrain file access [S23].
  7. Scheduled tasks need an honest "when does this run" story. Cowork's run only while the computer is awake and the app is open [S23]; unattended cloud runs need a different trust model.
  8. Computer use should prefer semantic handles to pixels. Accessibility-tree targeting hits real UI elements instead of guessed coordinates [S24].
  9. Credentials and untrusted content must never meet the model carelessly. Sealed endpoints: a broker holds the credential, enforces a fixed schema and per-tool egress allowlist, and returns only the parsed response [S29].
  10. Prompt injection is permanent. Design so a successful injection cannot cause harm; no single defense works; patterns include plan-then-execute, dual LLM (privileged plus quarantined), and context minimization [S29].
  11. Approvals scale badly unless designed. A "Runs inbox" with human-in-the-loop approvals is how OpenClaw-based managers surface decisions [S21]; Cowork adds per-tool permission stances [S23].
  12. Standards reduce lock-in and effort: MCP for tools, SKILL.md for procedures, ACP for editors [S26, S28, S27].

4. Product definition

4.1 What "agentic OS" can honestly mean

Level Description Examples Recommendation
L0 Chat assistant Chatbots Already exists in MiniMe
L1 Task agent with tools, user present MiniMake, Claude Code, Cowork MiniMake covers coding; MiniMate adds non-code tasks
L2 Background automations: scheduled and event-triggered, approvals via inbox Cowork scheduled tasks, ChatGPT scheduled execution [S23, S33] Target for U1–U2
L3 Always-on personal agent across channels with memory and learning OpenClaw, Hermes [S21, S22] Target for U2–U3
L4 Desktop-level agent that operates GUI apps and the system Cowork computer use, Linux desktop MCP servers [S23, S24] U4, attended first
L5 An operating system or appliance where the agent is the primary shell A MiniMate distro or device Only if demand is proven; not planned

Recommendation [P]: build L2, then L3 on Linux, then L4 under strict attendance rules. Treat L5 as a packaging decision (an image or a mini-PC "MiniMate box") made after real usage.

4.2 Who it is for and what they do with it [P]

Primary: Linux-using technical users, makers and small-team founders who want routine digital chores automated without trusting a black box, plus MiniMe/MiniMake users who already have projects and want ongoing maintenance.

Representative jobs (full list with costs in Appendix B):

  • Morning brief from calendar, mail and tasks; meeting prep.
  • Inbox triage with drafted replies that are never sent without approval.
  • File and download organization; receipt-to-spreadsheet reports.
  • Watch logs, backups and servers; alert only when something is wrong.
  • React to CI failures or dependency alerts by opening a MiniMake session.
  • Research digests on topics the user follows.
  • Home and workshop automation events.

4.3 Positioning

Promise: "An assistant that does your routine work in the background, shows you everything it did, and cannot do anything you did not allow."

4.4 Relationship to MiniMake [P]

  • One engine, two profiles. The server loop, tool broker, permission engine, session log, metering and device link are shared [MK §5, §6, §8, §13]. A profile selects: system prompt, tool set, default modes, available surfaces, and budgets.
  • MiniMake = coding profile: project folder, code tools, review roles.
  • MiniMate = automation profile: connectors, scheduler, memory, channels, desktop tools.
  • A MiniMate automation can start a MiniMake run (for example "when CI fails, open a session on repo X in plan mode and message me a summary"), and a MiniMake user can promote a repeated task to a MiniMate automation.
  • Branding choice [open]: MiniMate as the umbrella app with MiniMake as one skill pack, or MiniMake and MiniMate as sibling products sharing an account. The architecture supports both.

4.5 Principles

  1. Human in control by default; autonomy is earned per automation. Each automation starts attended and graduates to unattended after a trial run and an explicit policy.
  2. Least privilege, everywhere. Scoped folders, scoped connectors, scoped tools, scoped time.
  3. Reads are cheap, writes are gated, irreversible actions need a human.
  4. Everything is logged and replayable.
  5. Explain cost before and after. Your rulebook's "four numbers" rule [M].
  6. Open formats: SKILL.md, MCP, plain-text memory, exportable data.
  7. Fail closed. If policy, connector or model is unavailable, the automation pauses and tells the user; it never improvises.

4.6 Non-goals (v1)

Building a Linux distribution; a public marketplace; autonomous financial transactions; acting on behalf of the user in a way a third party cannot distinguish from the user (for example sending messages as the user) without explicit per-automation consent; Windows and macOS desktop control; training your own models.

5.2 Many brains, many hands

Anthropic's design lets any stateless harness connect to any number of "hands" exposed as execute(name, input) → string, and notes the harness need not know whether a hand is a container, a phone or an emulator; brains can pass hands to one another [S5]. For MiniMate this is the central idea: a user may have a laptop node, a home-server node, a cloud sandbox and connectors, all as hands; the orchestrator decides where each step runs and the policy engine on each hand enforces local rules.

5.5 Data flows

  • Scheduled run: scheduler fires → orchestrator creates run with the automation's policy and budget → loop executes; tool calls routed to hands; results logged → output delivered to the channel/inbox; any gated action becomes an approval card.
  • Message from a channel: gateway authenticates sender (paired allowlist), creates or resumes a session, loop runs, reply is sent back. Messages from unknown senders are not treated as user instructions (§11.7).
  • Approval: card appears in inbox and optionally on the channel; decision returns to the run; the node re-checks hard policy before executing.

6.2 The automation spec [P]

An automation is a file (YAML or TOML) stored in the user's account and optionally mirrored in ~/.minimate/automations/. It is created by talking to the Planner, then shown back to the user for approval.

id: morning-brief
description: Summarize my day and send it to Telegram at 07:30
trigger:
  type: cron
  schedule: "30 7 * * 1-5"
  timezone: Asia/Dhaka
  missed_run: skip_if_older_than_2h
agent:
  profile: automation
  model_class: S            # cheap by default; escalate rules below
  instructions: |
    Use today's calendar, unread priority mail and my task list. Keep it under 150 words.
capabilities:
  - connector: calendar      # read-only stance
    tools: [list_events]
  - connector: email
    tools: [search, read]    # no send
  - connector: tasks
    tools: [list]
  - channel: telegram
    tools: [send_to_me]
policy:
  tier_max: T2               # drafts and messages to the owner only
  unattended: true
  approvals: none_required   # all capabilities are read or owner-only output
  egress: [telegram.org]
budget:
  per_run_usd: 0.05
  per_month_usd: 2.00
quiet_hours: "22:00-06:30"
notify_on_failure: true
audit: full

Rules [P]: a spec cannot grant more than the user's account policy allows; capabilities lists exact tools; anything not listed is unavailable; the Planner proposes, a human approves; changes create a new version; dry-run mode runs the automation with all writes simulated and shows what it would do.

6.3 Run lifecycle and reliability

States as in MiniMake plus queued, skipped, awaiting_approval_unattended. Requirements:

  • Idempotency: each trigger event has an ID; duplicate events do not start duplicate runs (webhooks retry).
  • Concurrency: one active run per automation by default; queue or drop per spec.
  • Retries: transient failures retry with backoff up to N; permanent failures notify once, not repeatedly.
  • Missed runs: policy per automation (run_now, skip, run_if_recent). Cowork's scheduled tasks only run while the computer is awake [S23]; MiniMate must tell users plainly when a run depends on their node being online and offer the cloud-sandbox alternative.
  • Time zones and DST: store the zone with the schedule.
  • Observability: every run has a timeline (trigger, steps, tool calls, outputs, cost).

6.4 Heartbeat design (and its cost)

OpenClaw's heartbeat wakes the agent every 30 minutes (hourly on some auth modes), reads a checklist file, and acts or stays silent; an empty file skips the model call entirely [S21]. Costs add up:

[A] 4,000 input + 300 output tokens per beat (system, memory excerpt, checklist):

Interval Beats/month Input tokens Output tokens Luna-class ($0.20/$1.20) Sonnet-class ($2/$10)
30 min 1,440 5.76M 0.43M ≈ $1.67 ≈ $15.84
60 min 720 2.88M 0.22M ≈ $0.84 ≈ $7.92

(Prices from your rulebook [M]; no caching assumed, which makes these upper bounds for the Luna row.)

Design rules [P]:

  1. Gate before the model. The node or connector proxy runs cheap scripts first ("any new priority mail? calendar change? disk over 90%?") and only wakes the model if something changed.
  2. Empty checklist = no call.
  3. Cheapest class (F or S) for heartbeats; escalate only when action is required.
  4. Quiet hours and per-day beat caps.
  5. Per-automation monthly budget with a visible meter; pause and notify when exhausted rather than silently degrading [M rule 7].
  6. Default interval 60 minutes; 15-minute intervals only on higher plans.

6.6 Outputs

Every automation chooses where results go: the inbox, a channel message, a file, a draft in an app, or nothing (side effects only). Digests group routine outputs into one daily message to avoid notification spam. Failures and approvals are always delivered.

6.7 Unattended policy

Unattended runs are the main risk surface: no human is watching, and the content they read may be hostile. [P] Rules:

  1. Only capabilities listed in the spec; tier ceiling enforced by the node and connector proxy.
  2. Default unattended ceiling is T2 (reads, drafts, notifications to the owner, writes inside a designated workspace).
  3. T3 and above (messages to other people, changes to external systems, installs) require per-action approval even if the automation is "unattended": the action waits in the inbox with an expiry.
  4. Taint rule: if an unattended run reads untrusted content (web pages, inbound email bodies, shared documents) it loses all egress and external-write tools for the rest of the run (§11.4).
  5. Budget and step caps per run, per day.
  6. Anomaly stop: repeated denies, unexpected tool requests, or cost spikes pause the automation and notify.

7. Memory and knowledge

7.1 Layers

Layer What Format Loaded
Working Scratchpad for the current run Run-scoped file On demand
Episodic What happened each day (runs, decisions, outcomes) memory/YYYY-MM-DD.md, append-only Searched, not loaded wholesale
Semantic Durable facts and preferences about the user MEMORY.md, USER.md Index at start
Procedural How to do things Skills (SKILL.md) Description at start; body on use
Knowledge User-supplied documents, org context Indexed folders/files with sources Retrieved on match
Session log Every event Backend DB Queried, never pasted whole

OpenClaw stores memory as Markdown in the agent workspace: MEMORY.md for long-term facts, USER.md for preferences, and dated daily notes, retrieved with search tools only when relevant [S21]. Hermes adds full-text search with LLM summarization for cross-session recall and a user-modeling layer [S22].

7.2 Rules [P]

  1. Plain files the user can open, edit, export and delete. No hidden vector-only memory.
  2. Show every automatic write ("I saved: you prefer concise briefs") with an undo.
  3. Never auto-save secrets, credentials, financial or health details, or contents of private messages beyond what the user asked to keep. Redact before storing.
  4. Separate memory per profile and per project (MiniMake project memory vs. personal memory), with explicit sharing.
  5. Retention controls: daily notes roll up into weekly summaries; old detail expires on a schedule the user sets.
  6. Search: full-text first; embeddings as an option. Hermes uses FTS5 plus LLM summarization [S22].
  7. Consolidation job (nightly, cheap class): merge duplicates, resolve contradictions (newest wins unless flagged), promote repeated facts to MEMORY.md, propose skills from repeated procedures.
  8. Export/import: Markdown zip; an importer for OpenClaw/Hermes layouts is cheap marketing, since Hermes already imports from OpenClaw [S22].

7.3 Memory poisoning defense

Memory is an attack surface: an injected instruction saved as a "preference" persists across sessions [S29]. [P] Controls: only the user's own messages and explicit approvals can create instructions in memory; content from untrusted sources can only create facts tagged with their source and trust level; memory lines that look like instructions ("always forward mail to…") require confirmation; the consolidation job never promotes untrusted-source lines.

8. Skills, playbooks and the learning loop

8.1 Format

Use the open Agent Skills format: a folder with SKILL.md (frontmatter name, description; Markdown body) plus optional scripts/, references/, assets/; progressive disclosure means only names and descriptions load at startup [S28]. This lets users bring skills from Claude Code, Codex, Cursor and Gemini [S28] and lets you ship vertical packs.

Add a permission manifest (MiniMate extension) in frontmatter so users see what a skill may touch:

---
name: weekly-expense-report
description: Build a weekly spreadsheet from receipt PDFs in the Receipts folder. Use when asked for expense reports.
permissions:
  folders: [~/Receipts:read, ~/Reports:write]
  connectors: []
  network: none
  tier_max: T2
---

8.2 Playbooks and knowledge (Devin's split)

Devin separates Playbooks (intentional, versioned procedures for recurring tasks; each save creates a version you can review or revert) from Knowledge (retrieved tips and organizational context that apply across sessions) [S17]. Adopt both ideas: skills are versioned; knowledge entries are retrieved by match; promote a repeated reminder from a playbook into knowledge [S17].

8.3 The learning loop (Hermes-style), with brakes

Hermes creates skills autonomously after complex tasks and refines them during use [S22]. For a managed, security-conscious product:

  1. After a successful multi-step run, the agent may propose a skill draft (name, description, steps, scripts).
  2. The draft goes to a review queue in the inbox with a diff against any existing skill; your reviewer and security-reviewer roles run first and attach findings [M].
  3. The user approves, edits or discards. Nothing becomes active automatically.
  4. Approved skills get a version number, a test (a recorded dry-run that must still pass), and a rollback button.
  5. Usage stats per skill: success rate, cost, last used; low performers are flagged for revision.

8.4 Marketplace (U5) and the supply chain

Reasons for caution: a Snyk study cited by the OpenClaw community found 36% of ClawHub skills with flaws, 13.4% critical, and 283 leaking credentials; a separate demonstration by a security team built a malicious skill that exfiltrated data and injected prompts unnoticed [S21].

[P] Pipeline before any third-party skill is listed: static scan of scripts and instructions; permission manifest required and enforced at runtime; sandboxed trial run with canary secrets; publisher identity verification; signing; versioning with the ability to yank; rating only after verified installs; default off for community content; first-party and verified-publisher tiers first.

9. Connectors and integrations

9.1 Principles

  1. MCP-first. Connectors are MCP servers (local or remote) behind your connector proxy.
  2. Tokens live in the vault; the model sees results. Anthropic's Managed Agents design stores OAuth tokens in a secure vault and routes MCP calls through a proxy that fetches credentials per session, so the harness never sees them [S5].
  3. Read and write are separate capabilities with separate stances: allow, ask, block, per tool, as Cowork offers [S23].
  4. Sealed endpoints for sensitive actions. A broker process holds the credential, executes a fixed-schema call, enforces a per-tool egress allowlist, and returns only the parsed response [S29].
  5. Least scope on OAuth. Request read-only scopes by default; escalate per automation.

9.2 What MCP 2026-07-28 changes for you [R:S26]

  • No protocol-level sessions or session-ID header on Streamable HTTP; each request carries version, client identity and capabilities; easier to scale statelessly.
  • Tasks extension for long-running work: the server returns a task handle; you poll tasks/get and can send input with tasks/update. Good fit for connector operations that take minutes.
  • Elicitation without an open stream: servers can ask for user input as part of the request flow, which maps onto your approval inbox.
  • Authorization tightening: OAuth 2.1/OIDC, issuer binding for stored credentials, Client ID Metadata Documents instead of dynamic client registration (deprecated, still available).
  • Feature lifecycle: deprecations get at least twelve months; plan for upgrades rather than surprises.

9.3 Connector catalog by priority [P]

Tier Connectors Why
1 (U2) Email (Gmail/IMAP), calendar, tasks, Telegram, a files provider (local node + Drive) Daily-brief, triage and organization use cases
2 Slack, WhatsApp (via business API or bridge), GitHub, Notion, Discord, Signal Team and developer workflows
3 Home Assistant, RSS/pollers, Spreadsheets (Sheets/Excel via skills), browser automation Maker and research use cases
4 CRM, accounting, banking-read-only Only with strong governance; banking write is a non-goal

Cowork's vertical bundles show how connectors, skills and plugins can be packaged per function (for example, a legal bundle with 12 plugins and 20+ connectors) [S23]; copy that packaging for "Maker", "Founder" and "Developer" bundles later.

9.4 Connector SDK (for you and later partners)

A connector declares: name, auth method, tools with JSON schemas, per-tool risk tier, read/write class, egress domains, rate limits, and test fixtures. Your proxy validates arguments against the schema, applies the stance, injects credentials, calls out through the egress allowlist, and returns a size-capped parsed result. Tool descriptions from third-party servers are untrusted and shown to the user before first use.

10.2 Desktop control ladder

Prefer the highest rung that works; each lower rung is slower, less reliable and riskier.

  1. APIs and CLIs (gh, xdg-open, libreoffice --headless, ffmpeg, pandoc, database CLIs): deterministic, auditable.
  2. App-specific connectors/MCP servers.
  3. Accessibility tree (AT-SPI): read widget roles and names, invoke semantic actions; "role plus name → element" is the robust default, and fusing a screenshot with the tree lets actions be addressed semantically instead of by guessed coordinates [S24]. Requires enabling accessibility and may need to silence the screen reader [S24].
  4. Screenshots plus vision via the screencast portal (this may trigger a user permission prompt each time [S24]).
  5. Raw input synthesis (ydotool on Wayland, xdotool on X11): last resort. computer-use-linux supports Wayland-first with X11 best-effort across GNOME, KDE/KWin, Hyprland, i3 and COSMIC [S24].

Wayland caveats [R:S24]: compositors restrict screenshots, input injection and window control; support differs per desktop; portals ask for consent; some features need compositor-specific helpers (COSMIC has its own). Treat desktop control as best-effort per compositor and say so in doctor.

10.3 Where desktop work runs

Situation Where Why
User present, supervising User's real desktop, attended Needed for their apps; every action visible; kill switch (Cowork's computer use runs outside the VM on the actual desktop and is limited to higher plans, which signals the risk [S23])
Unattended GUI work Headless virtual desktop in a sandbox (Xvfb or headless Wayland in a container/microVM) No access to the real session; disposable
Web tasks Dedicated browser profile in a container or on the node Not the user's logged-in daily profile
Untrusted files or sites Cloud sandbox Blast radius is the sandbox

10.4 Privilege and system management

  • No root by default. System changes (install packages, edit /etc, manage services) are a separate capability tier (T4).
  • Use polkit prompts or a dedicated, narrowly scoped sudoers rule per command with an approval card that shows the exact command; never a blanket sudo.
  • Package changes go through the distro package manager inside a snapshot-aware flow when possible (btrfs/snapper, or apt/dnf with a recorded undo plan).

10.5 Isolation technologies (choose by tier)

Tier of work Isolation Examples
Local read-only helpers Process-level Landlock, seccomp
Local shell and file work bubblewrap namespaces, Landlock + seccomp, network proxy Same as MiniMake [S3, S9]
Untrusted web/documents Container (Podman) with default-deny egress
Hostile or high-risk MicroVM (Firecracker-style) or gVisor-class sandbox Gemini CLI lists Seatbelt, Docker/Podman, gVisor and a Windows sandbox among its sandbox options [S15]

10.6 Distribution forms

  1. Package + installer script (curl | bash, .deb, .rpm, AUR, Flatpak for the UI): U3.
  2. Preconfigured VM or container image for people who want isolation from their main machine: U4.
  3. "MiniMate box" (mini-PC or Raspberry Pi image) for an always-on hub: U5 only if demand appears.
  4. A bootable distro: not recommended. It multiplies maintenance (kernel, drivers, updates, security patches) for little gain over a service plus an image.

10.7 Other operating systems

macOS and Windows are strategically important (Cowork supports them [S23]) but sandboxing and desktop control differ. Plan later support: macOS via Seatbelt and Accessibility APIs; Windows via WSL2 for sandboxed shell and UI Automation for desktop. Do not promise them for v1.

11. Security and trust model

This is the most important section. If you must cut something, cut features before this.

11.1 Threats specific to MiniMate

Threat Why it is worse than in a coding agent
Indirect prompt injection via email, web, documents, chat messages The agent reads untrusted inbound content continuously and often unattended [S29]
Messages from strangers treated as commands Channels expose the agent to anyone who can message it
Credential theft and misuse Connectors hold the keys to the user's mail, files and chat
Skill/plugin supply chain Marketplace skills ran with real credentials in the OpenClaw ecosystem [S21]
Memory poisoning Persists across sessions [S29]
Over-broad scheduled access A bad automation runs every day
Desktop control mistakes GUI actions are hard to undo
Cost abuse Triggers and heartbeats multiply runs
Account/channel takeover Someone gains the ability to talk to the agent

11.2 Capability tiers

Tier Examples Approval (attended) Approval (unattended)
T0 Observe Read files in a granted folder, list calendar, search mail metadata None Allowed
T1 Derive Create summaries, drafts, reports in a designated workspace None Allowed
T2 Notify owner Message the owner, create a draft in the user's own mailbox, write to the workspace None Allowed
T3 Act externally (reversible) Send an email/message to others, create calendar events with invitees, post to a channel, open a PR Ask (show exact content) Per-action approval in the inbox
T4 Change system or data Install packages, edit system config, delete/move many files, modify external records Ask with diff/undo plan Not allowed unattended
T5 Irreversible or financial Payments, account changes, destructive deletes, publishing Ask with confirmation phrase Never unattended

Each connector tool and each local capability is assigned a tier by its author and re-rated by you; users can only lower, never raise, the ceiling beyond what the account policy allows.

11.3 Breaking the lethal trifecta by construction

The trifecta is private data + untrusted content + external communication [S29]. Patterns [P], drawn from the design-pattern literature and practitioner guidance [S29]:

  1. Split agents. A reader agent processes untrusted content (inbound mail, web) with no egress and no external-write tools, returns a short structured result; an actor agent with write tools sees only that structured result and the owner's instructions. This is the dual-LLM idea: a privileged model decides, a quarantined one reads untrusted input [S29].
  2. Plan, then execute. Generate the plan before untrusted content is read; execution follows the fixed plan and cannot add tools based on what it reads [S29].
  3. Context minimization: pass the smallest necessary slice of untrusted content (for example, the sender, subject and a sanitized snippet, not the full body) [S29].
  4. Egress allowlists per automation (domains and recipients); default deny.
  5. Taint tracking: once a run ingests untrusted content, it loses tools that can leave the boundary (§6.7, [MK §8.6]).
  6. Sealed tool endpoints that accept fixed schemas only (for example, send_to_owner(text) with no free-form recipient) [S29].

11.4 Unattended policy summary

See §6.7. Put the rule in one line for users: "Unattended automations can read and draft, and can message only you; anything that touches other people or systems waits for your approval."

11.5 Credentials and secrets

  • Vault with envelope encryption; per-user keys; hardware-backed key storage for the node where available.
  • Tokens are scoped, short-lived where the provider allows, and bound to the issuer that granted them (MCP spec requires clients to key credentials by issuer and not reuse them with a different authorization server [S26]).
  • The model never sees tokens; the sandbox never holds them [S5].
  • Secrets scanning on inbound and outbound content; canary tokens in sandboxes to detect exfiltration attempts.
  • A panic button: revoke all tokens, stop all runs, disable all automations, in one action.

11.6 Gateway hardening (from OpenClaw's practice) [R:S21]

Bind the local gateway to loopback; require token authentication; run tools in a sandbox; scope file access; review skills before installing; provide a security audit command; never run as root. These are defaults in MiniMate, not options.

11.7 Channel security

  • Pairing: a channel account becomes "the user" only after an out-of-band pairing (code shown in the web app); everyone else is a stranger.
  • Strangers' messages are data, not instructions. They can be summarized for the owner but never trigger tools.
  • Sender allowlists, rate limits, and spoofing checks (for example, verified WhatsApp/Telegram IDs, signed webhooks).
  • Group chats: the agent responds only when addressed by a paired user; group content is untrusted.

11.8 Audit, replay and privacy

  • Every run has an immutable timeline; users can export it and delete it on a schedule.
  • Privacy: list sub-processors (model providers, search, sandbox vendor) as your rulebook requires [M]; redact before external model calls; offer a "local-only memory" toggle.
  • Data residency: note which region stores logs; offer deletion on request.
  • Children and sensitive categories: do not store sensitive personal data in memory by default.

11.9 Abuse prevention for a managed service

  • Per-user rate limits, concurrent run limits, and budget caps on all triggers.
  • Outbound message limits per channel to prevent spam use.
  • Sandbox egress allowlists and quotas to block scanning, mining and abuse of your infrastructure.
  • Terms that prohibit misuse; automated detection of suspicious patterns; a fast kill path for a user or automation.

11.10 Incident response

Runbook for: leaked token, malicious skill discovered, injection that caused an action, compromised device. Include revoke-all, notify-users, forensic export, and a public postmortem habit. The OpenClaw ecosystem's experience (public security studies and demonstrations [S21]) shows that agent incidents become public quickly.

11.11 Testing the safety claims

Build the red-team suite before U2 ships: injection through mail, web, calendar invites, filenames, document metadata, MCP descriptions; stranger messages; skill exfiltration attempts with canary secrets; sandbox escapes; heartbeat abuse; memory poisoning. A release is blocked if any "no unapproved egress or external write" test fails.

12. Surfaces and UX

12.1 The Runs inbox (the heart of the product)

One screen (web, mobile web, and a TUI view) shows every automation and run:

Section Contents
Needs you Approval cards, review-queue items (skill drafts), failures needing a decision
Running now Live runs with a step timeline and a Stop button
Recent Completed runs, outputs, cost, "what changed" summaries
Automations List with status, next run, monthly cost meter, pause/edit/dry-run
Memory & skills Browse and edit memory files and skills; review proposed ones

OpenClaw-style managers surface human-in-the-loop approvals in a Runs inbox for the same reason: unattended agents need one place where decisions accumulate [S21].

Approval card [P]: what the agent wants to do in plain words; the exact content (email text, command, file diff); which automation and why; tier; what happens if you do nothing (expires, skipped); buttons Approve once / Approve and remember for this exact action / Edit / Deny / Deny and pause automation. Approvals expire (default 24 h) and never auto-approve.

12.2 Creating an automation

  1. User describes it in plain language ("every weekday at 7:30 send me a brief on Telegram").
  2. The Planner proposes an automation spec (§6.2) and lists capabilities and tiers in plain words.
  3. Dry run immediately, with all writes simulated, showing what it would have done.
  4. User approves; it starts attended (outputs go to the inbox for N runs).
  5. After N clean runs the UI offers to graduate it to unattended with its policy shown.
  6. Any later change to capabilities re-triggers review.

12.3 Reversibility and undo

Class Examples Undo
Reversible by snapshot File edits in granted folders Checkpoints per run [MK §11.1]
Reversible by action Drafts, calendar events you created, labels "Undo" button performing the inverse
Delayed Sending email with a configurable delay window Cancel before send
Irreversible Sent messages, payments, deletions beyond trash Approval with confirmation; never unattended

Be explicit in the UI about which class an action is in, as Claude Code is about checkpoints not covering remote effects [S2].

12.4 Channels

Start with web inbox + Telegram + email-to-owner, then Slack and WhatsApp. For each channel: pairing flow, message formatting (short, scannable), approval buttons where supported, rate limits. Messages from strangers are data (§11.7). Digest mode groups routine output into one message a day.

12.5 Voice (U4)

Push-to-talk and voice notes through channels first; always-listening is a non-goal. Reuse the speech-to-text and text-to-speech providers already in your stack [M]; treat transcribed audio like any user message (it is only trusted after device/channel pairing).

12.6 Terminal and desktop

  • minimate TUI shares the MiniMake TUI components [MK §12]: chat, tasks, approval prompts, status line with tier, taint and cost.
  • Desktop notifications for approvals; a tray icon (optional) with Pause All.
  • Quick-ask hotkey that sends the current selection or a screenshot to MiniMate (U4).

12.7 Onboarding

minimate login (device code) → minimate doctor (sandbox, accessibility, portals, service) → choose folders to grant → connect one channel and one connector → pick a starter automation (morning brief) → dry run → approve. Target: first useful automation in under ten minutes.

12.8 Cost transparency

Per automation: cost last run, this month, budget remaining. Account-level: your rulebook's four numbers (used, left, resets, what a run will cost) [M]. Estimated cost range before enabling an automation, based on its spec.

13.4 Metering

  • Use the agent credits approach from MiniMake [MK §14.4]: a credit approximates cost; show "about N automation-runs left".

13.5 Pricing method

Same rule as MiniMake: price ≥ COGS at the cap ÷ 0.45 [M, MC §14.5]. Compute COGS for a user who exhausts every meter on the default chain, including sandbox minutes and connector proxy costs. Compare against consumer agent plans (ChatGPT Agent is bundled into paid ChatGPT tiers; Cowork requires paid Claude plans; Manus and others price by credits [S33, S23]) and your regional price rungs [M]. 13.6 What to protect

  • No free production usage with agent actions; at most a tiny capped trial per verified identity [M rule 1].
  • Outbound message and sandbox quotas to prevent spam and abuse (§11.9).
  • Degrade gracefully, never silently: when a budget ends, pause and say so [M rule 7].
  • Bound the long tail: a single noisy automation must not exceed a daily dollar cap.

14.1 Metrics

Run success and abandonment; approval rate and time-to-approve; denied/expired approvals; false-positive alerts per automation (notification fatigue); cost per run and per automation; heartbeat skip rate (how often the pre-check avoided a model call); injection-suite pass rate; connector error rate; time-to-first-useful-automation; weekly active automations per user.

Same event log as MiniMake [MK §15.3]: timeline per run, model calls, tool calls, approvals, costs. Provide the user a filtered export; keep the internal log immutable.

16. Risks and open decisions

16.1 Top risks

Risk Likelihood Impact Mitigation
A successful prompt injection causes an external action or data leak High Severe Tiers, split agents, sealed endpoints, taint, egress allowlists, approvals for T3+
Credential compromise Medium Severe Vault + proxy, scoped OAuth, panic button, canary tokens
Heartbeat/trigger cost explosion High High Pre-checks, budgets, quiet hours, per-automation caps
Marketplace supply-chain incident Medium (if opened early) Severe No marketplace until scanning and signing; first-party skills only
Memory poisoning Medium High Source-tagged memory; instructions only from owner
Wayland/desktop-control fragility High Medium Ladder, attended-first, per-compositor claims in doctor
Notification fatigue and over-automation High Medium Digests, graduation flow, noisy-automation detector
Scope explosion ("agentic OS") High High Stage gates; no distro; L2/L3 first
Regulatory/privacy exposure (mail and files pass through your servers) Medium High Redaction, retention controls, sub-processor disclosure, local-only memory option
Solo-founder capacity High High Shared engine with MiniMake; ship U0–U2 before anything else
Fast-moving ecosystem and rebrands High Medium Build on MCP, SKILL.md, ACP

16.2 Open decisions

  1. Umbrella vs sibling branding for MiniMake and MiniMate (§4.4).
  2. Which two or three channels first (Telegram and email are the cheapest).
  3. Cloud sandbox vendor and per-minute pricing.
  4. Whether unattended T3 approvals use push notifications on mobile (requires a mobile surface) or channel buttons.
  5. Whether to offer a self-hosted node image early.
  6. Memory export formats and importers (OpenClaw/Hermes layouts).
  7. How aggressive the learning loop should be by default (recommended: propose only, never auto-enable).
  8. Regional rollout: payment methods and languages (your rulebook already covers regional price rungs [M]); decide whether Bangla language support and voice are early features for your home market.

Appendix A — Feature summary (adopt / adapt / build)

Adopt: durable runs, scheduler, heartbeat with checklist (gated), Markdown memory, FTS search, SKILL.md, MCP, per-tool stances, vault + proxy, loopback/token defaults, folder grants, sandboxed shell, AT-SPI-first desktop control, doctor, Runs inbox. Adapt: heartbeat cost controls, agent-curated memory (with undo), autonomous skill drafting (review queue), mobile handoff, headless virtual desktops, computer use outside sandbox (attended only), machine snapshots, vertical bundles. Build (MiniMe-only): automation spec with tiers and policy, unattended policy engine, split reader/actor agents, sealed endpoints, taint tracking across automations, approval inbox with expiry, per-automation budgets, graduation flow, reviewer/security-reviewer gate on skill drafts and risky actions. Later: user modeling, self-improving skills, wide parallel agents, screen-recorded verification, marketplace, Windows/macOS, appliance. Skip: building a distro, autonomous financial actions, always-on microphone.

Appendix D — Linux hardening checklist

  • Node runs as the user, never root; systemd unit with NoNewPrivileges, ProtectSystem, PrivateTmp where compatible.
  • Loopback binding; token auth; TLS to the backend.
  • bubblewrap/Landlock profile; network via local proxy with allowlist.
  • Folder grants only; .git, config and secrets read-only/denied.
  • Sanitized environment; secrets scanning on outputs.
  • Desktop control disabled unless the user enabled it and doctor passes.
  • Package changes only through approval cards with exact commands.
  • Panic button reachable from tray, CLI and web.

Appendix E — What to cut first if time is short

  1. Voice. 2. Desktop control. 3. Marketplace. 4. Learning loop (keep manual skill creation). 5. Extra channels. 6. Compare-runs and parallel fan-out. Never cut: tiers, unattended policy, vault/proxy, audit log, red-team suite, kill switch.

Appendix F — Glossary

Automation: a saved task with trigger, capabilities, policy and budget. Heartbeat: periodic low-cost wake-up reading a checklist. Tier (T0–T5): capability risk class. Reader/actor split: separating agents that read untrusted content from agents that can act. Sealed endpoint: a broker that holds credentials and accepts only a fixed schema. Taint: marker that untrusted content has entered the run. Node: the local Linux service. Gateway: the channel and session front door. Runs inbox: the place for approvals and results. Graduation: moving an automation from attended to unattended.
