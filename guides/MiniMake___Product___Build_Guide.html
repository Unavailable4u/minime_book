0. How to read this guide

What this is. A complete specification of MiniMake, the coding agent that runs on the user's machine and gets its intelligence from the MiniMe backend. It is built from (a) research across about 30 tools, docs and papers collected on 2026-10-02, (b) your Financial Strategy Rulebook, Technical Roadmap and old CLI plan, and (c) what I read in your repository and system-explanation diagrams in earlier turns.

1. Executive summary

MiniMake in one paragraph. A terminal-first coding agent that executes tools on the user's own machine while the reasoning loop, model routing, project context, review panel and metering live on the MiniMe backend. It reads and edits files, runs commands in an OS-level sandbox, plans before acting, keeps checkpoints so any change can be undone, and can be driven from the terminal, from editors (through ACP) or remotely from the MiniMe web app. Its edge over Claude Code and Codex is not a better loop; it is MiniMe's project context, multi-model orchestration, security-review pipeline and cost control, offered as one premium product.

The ten decisions this guide makes

  1. Brain on the server, hands on the machine, durable session log in between. Anthropic published exactly this pattern for its Managed Agents service and gave reasons that match your situation [R:S5]. It also fits your existing daemon bridge.
  2. The harness is the product. On the Terminal-Bench 2.0 data in one survey, the same model (Claude Opus 4.6) scored 58.0% in Claude Code and 76.4% in a different harness, an 18-point spread [R:S25]. Loop quality, tool design and context handling matter as much as the model.
  3. Small tool set, progressive disclosure, grep-first search. Claude Code runs about 20 tools and the team says the bar to add one is high [R:S6]. They removed over 80% of the system prompt for the Claude 5 generation with no measurable loss on their coding evals [R:S7].
  4. Layered safety, enforced locally. Permission modes, allow/ask/deny rules, an OS sandbox for shell commands, hooks, and a classifier for an "auto" mode. The local client enforces hard limits even if the backend says "approved" [R:S3, S4] [P].
  5. Adopt open standards instead of inventing formats. AGENTS.md, SKILL.md (Agent Skills), MCP, and ACP for editor integration [R:S26, S27, S28]. This is how you "use VS Code" without building an editor.
  6. Checkpoints, resumable sessions, worktrees, parallel agents are table stakes now, found in Claude Code, Codex, Cline, Cursor and Gemini CLI [R:S2, S15, S16].
  7. MiniMe's moat: project context (instructions, parts, wiring, wireframes), your reviewer and security-reviewer roles, model-tier routing, and the browser app as a control surface [M].
  8. Meter by agent credits, not raw tokens. Agent loops re-read context every step, so the rulebook's "cached tokens count fully" rule would drain a user's pool in a few sessions [M] (§14).
  9. Use cheap-but-strong models for the main loop. On Terminal-Bench 2.1, GPT-5.6 Luna scored 75.7% and Claude Sonnet 5 scored 74.6%, at a fraction of the price [R:S25] [M]. Test with your own eval before relying on this.
  10. Gate release on security. Invite-only beta first, external audit before general availability [M], consistent with how Codex, Cline and Claude Code all treat shell access as the main risk [R:S9, S13, S4].

2.2 What the benchmarks say, and how far to trust them

  • Terminal-Bench 2.1 (leaderboard snapshot dated 2026-09): GPT-6 Astra in Codex CLI 87.4%, Claude Fable 5 in Claude Code 83.8%, GPT-5.5 in Codex CLI 83.1%, Claude Opus 4.8 78.9%, GPT-5.6 Terra 78.4%, GPT-5.6 Luna 75.7%, Claude Sonnet 5 74.6% [R:S25]. Another tracker reported Codex with GPT-5.6 Sol at 89.5% and Claude Code with Opus 5 at 89.1% in an independent run [R:S25].
  • Harness spread is large. One survey found Opus 4.6 ranging from 58.0% in Claude Code to 76.4% in a research harness, and GPT-5 ranging from 33.9% in a minimal harness to 49.6% in Codex CLI, differences "substantially larger than the standard errors" [R:S25].
  • Cost spread is large too. In one test of three harnesses on two self-hosted models, accuracy varied by about 8 points while spend varied about 2x; on one model Codex solved one more task than Claude Code for half the GPU time [R:S25].
  • Retrieval is contested. Anthropic's tool team moved from vector indexing to grep because Claude could build its own context [R:S6]. Several May–July 2026 measurements instead favored indexed retrieval, with one vendor-run test reporting 70%+ quality gains [R:S31]. Treat all of these as claims to test in your own eval.
  • Caution. These are leaderboards and vendor posts. They tell you where to look, not what your users will experience.

2.3 Twelve lessons from the research

  1. The loop is simple; everything around it is hard. Claude Code describes three blending phases: gather context, act, verify [R:S2]. The surrounding work is context, safety, extensibility and reliability.
  2. Separate brain, hands and session. Anthropic found that putting all three in one container made the server a "pet": a crash lost the session, debugging was blind, and credentials sat next to model-generated code [R:S5].
  3. Credentials must never be reachable from where model-generated code runs. Their fix: tokens live in a vault or are wired into git remotes at setup, and MCP calls go through a proxy that fetches credentials per session [R:S5].
  4. The session log is not the context window. Keep the full event log durable outside the model's context and let the harness decide what to show [R:S5]. OpenHands makes the same choice with an append-only event stream that enables replay [R:S20].
  5. Harness assumptions go stale as models improve. Context resets that helped Sonnet 4.5 were dead weight on Opus 4.5 [R:S5]; to-do reminders that helped older models constrained newer ones [R:S6].
  6. Fewer rules, more judgment. For newer models, examples in tool descriptions constrained exploration; expressive parameters worked better; repeated instructions could be deleted [R:S7].
  7. Progressive disclosure beats upfront loading. Skills load descriptions first and bodies on demand; MCP tool schemas are deferred behind tool search [R:S1, S7].
  8. Guardrails belong in code, not prompts. "A request in CLAUDE.md is not a guarantee; a PreToolUse hook that blocks is enforcement" [R:S1].
  9. Sandbox plus permissions, not either alone. Claude Code pairs a bubblewrap/Seatbelt sandbox with permission modes; Codex pairs sandbox modes with approval policies [R:S3, S9]. Without filesystem isolation, a compromised agent can backdoor system resources to reach the network [R:S3].
  10. Reversibility is a feature. Checkpoints (Claude Code, Cline, Gemini CLI, Replit) and git-based undo (Aider, Codex) make autonomy tolerable; remote actions cannot be checkpointed and need permission rules instead [R:S2].
  11. Extension marketplaces are an attack surface. Snyk's February 2026 study, as cited by the OpenClaw community glossary, reported 36% of ClawHub skills with security flaws, 13.4% critical, 283 leaking credentials [R:S21].
  12. Open standards won. SKILL.md is now an open spec adopted by Claude Code, Codex, Cursor, Gemini CLI, OpenClaw and others [R:S28]; ACP is the LSP of agents [R:S27]; MCP's July 2026 spec made servers stateless and moved long-running work to a tasks extension [R:S26].

4. Product definition

4.1 Positioning

  • For whom: MiniMe users who generate projects in the browser and want to continue on their own machine with real toolchains, plus developers who want a cheaper, more controllable alternative to Claude Code or Codex [P].
  • Promise: "The agent that already knows your project, runs on your machine, shows you everything it does, and can be undone."
  • Why switch from Claude Code or Codex: (1) it starts with your MiniMe plan, wireframes and instructions; (2) it uses the best-value model for each step instead of one vendor's model; (3) every change can be reviewed by your reviewer and security-review roles before you accept it; (4) one bill and one cost meter; (5) it connects to the browser app for handoff and remote control [M][P].
  • Honest competitive picture: Claude Code and Codex lead public terminal benchmarks [S25]. MiniMake should not claim to beat them on raw coding skill at launch. It should win on context, cost, review and integration.

4.2 Principles

  1. Local execution, server reasoning. Code never runs on your servers.
  2. Nothing irreversible without a human. Approval is local and cannot be bypassed by the backend.
  3. Small and legible. Few tools, few modes, short prompts.
  4. Open formats. AGENTS.md, SKILL.md, MCP, ACP.
  5. Measure everything. Cost per task, success per task, approval rate, rewind rate.
  6. Degrade gracefully. If a model fails or quota runs out, the run pauses with a clear message; it never silently switches to something worse (rulebook rule) [M].

4.3 Non-goals (for v1)

  • A full IDE, debugger or extension system. Use ACP and the user's editor.
  • A plugin marketplace.
  • Local models (maybe later through the same chain mechanism).
  • General personal automation. That is MiniMate.
  • Windows-native sandboxing. Support WSL2 first; Claude Code's own sandbox also requires WSL2 on Windows [S3].

5. Architecture

5.1 The shape: brain, hands, session

Anthropic's engineering team describes three virtualized parts of an agent: a session (an append-only log of everything that happened), a harness (the loop that calls the model and routes tool calls), and a sandbox (where code runs and files are edited), each replaceable without disturbing the others [R:S5]. MiniMake maps onto this directly:

5.2 Why this split is right for MiniMe

  • Your daemon already connects outward to the backend, so it works behind home routers and needs no inbound ports [M].
  • A crash on either side is survivable. The session log lives outside both. A new worker can pick a run up from the last event; a reconnecting client can ask for events after the last one it saw. This is the wake(sessionId) / getSession / emitEvent idea from Managed Agents [S5].
  • Time to first token improves when the brain starts without waiting for a sandbox; Anthropic reported roughly 60% lower median and over 90% lower p95 time to first token after decoupling [S5].
  • Provider keys and prompts stay on your servers. The client never holds model keys.

5.3 Trust boundaries

Component Trusted for Not trusted for
Local policy engine Final say on whether a tool call may run; hard denies; sandbox setup Nothing; it is the root of trust on the device
Backend Reasoning, routing, metering, classifier suggestions Approving anything the local policy denies; reading secrets; choosing the sandbox
Model output Nothing. It is untrusted input to the policy engine
Tool results (files, web pages, MCP responses) Nothing. Treated as data, labeled by trust level
Skills, hooks, plugins Only after install review; project-level ones prompt for trust on first use

5.4 Deployment: one codebase, separate process

[P] Do not copy the repository. Create a second entry point in the same repo that imports the shared orchestration core and leaves out chat, notebooks, research and other tabs. Reasons: improvements to routing, metering and guards then benefit both products; keys, ledger and plans stay single-sourced (your rulebook wants one meter and one price list) [M]. Keep it a separate process because your current backend runs one uvicorn process with a small agent thread pool and per-request deadlines, and long agent sessions plus WebSockets should not compete with chat traffic [M].

Suggested layout:

backend/
  eo/                    # shared orchestration core (existing)
  utils/                 # shared (llm_client, quota, audit, redaction)
  minimake/              # NEW
    server.py            # FastAPI app: /v1/code/*, /ws/device
    loop.py              # agent loop executor
    tools_schema.py      # tool JSON schemas + risk levels
    context.py           # prompt assembly, compaction, caching plan
    session_log.py       # append-only events, replay, cursors
    policy_classifier.py # auto-mode classifier
    review.py            # reviewer / security-reviewer hooks into eo roles
    metering.py          # agent credits, per-run ceilings
    devices.py           # device pairing, credentials, revocation
daemon/ → minimake/      # client (rename; keep path_guard, tools)

5.5 One step, end to end

  1. User types a task. CLI sends user_message over the device socket.
  2. Backend appends the event to the session log, assembles context (system prompt, MINIMAKE.md content sent by the client, rules matched to files, memory, recent history), picks a model, calls it with tool schemas.
  3. Model streams text and returns tool calls. Backend streams text_delta events to the client and appends them.
  4. For each tool call, backend sends tool_proposed with a call ID.
  5. Client policy engine decides: allow (rule or mode), ask (render approval prompt), or deny. A PreToolUse hook may block or modify it.
  6. If allowed, the client runs the tool (in the sandbox for shell), redacts secrets from the output, truncates it, and sends tool_result.
  7. Backend appends the result, updates budgets, loops to step 2 until the model stops, a limit hits, or the user cancels.

6. Agent loop and orchestration

6.1 The loop

run(run_id):
  state = load_or_create(run_id)                  # from session log
  while state.status == RUNNING:
      guard = run_guard.check(run_id)             # cancel flag, failure breaker, budgets
      if guard.stop: pause_or_end(guard.reason); break

      ctx   = assemble_context(state)             # §9; stable prefix, cache plan
      model = route(state.mode, state.step, state.signals)
      reply = model.call(ctx, tools=visible_tools(state))   # streamed
      emit(reply.text)                            # to client + session log

      if reply.tool_calls:
          for call in reply.tool_calls:           # parallel when independent
              result = broker.execute(call)       # remote call to client; policy applied there
              append_result(state, call, result)
          meter(state, reply.usage)
          verify_hooks(state)                     # diagnostics, lint/test if configured
      else:
          if stop_hooks_allow(state): state.status = COMPLETED
          else: append_hook_feedback(state)       # forces the model to continue

Notes grounded in the research:

  • The loop is deliberately boring. Claude Code's own description is three blending phases of gathering context, acting, and verifying, repeated until done, with the user able to interrupt at any time [S2].
  • Parallel tool calls matter for latency: batch independent reads and searches in one step.
  • Stop is a decision, not just "no tool calls". A Stop hook can refuse to let the run end (for example "tests must pass"), as Claude Code hooks can [S34].

6.2 Run states

created → running ⇄ awaiting_approval → completed
              │             │
              ├─► paused_budget ──(grant more)──► running
              ├─► paused_disconnected ──(reconnect)──► running
              ├─► paused_error ──(retry/switch model)──► running
              └─► cancelled | failed | expired
  • Persist status, step, mode, model_chain_position, budget_spent, last_event_seq, and taint in the database; append every event to the session log (§13.3).
  • While waiting for approval or reconnect, no worker thread is held; the run is just rows. A queue or timer resumes it [M: your current pool is small].
  • Expire idle paused runs after a configurable time (suggest 24 h) and tell the user.

6.4 System prompt principles

The July 2026 context-engineering guidance from the Claude Code team is the best current reference [R:S7]:

  • Say what the product is and what it is doing; cut the rest. They removed over 80% of the system prompt for the newest models with no measurable loss on their coding evals.
  • Prefer judgment to rules. Instead of "never write comments", say "match the surrounding code's comment density, naming and idiom".
  • Put tool usage in tool descriptions, not in the system prompt, and skip examples. Examples can narrow how the model explores. Design expressive parameters instead (for example, an enum for task status hints at how to use it).
  • Progressive disclosure. Move verification and review procedures into skills; defer rarely used tool schemas behind tool search.
  • Re-evaluate on each model upgrade. Keep a prompt eval so you can delete rules that older models needed. [P] Version the system prompt per model family in the model router.

6.5 Plan mode, questions, tasks

  • Plan mode: the visible tools are read-only plus ExitPlan. The model writes a plan; the user approves, edits or rejects. Cursor's plan mode produces a reviewable markdown plan [S16]; Claude Code, OpenCode and Cline have the same split [S1, S14, S13].
  • Questions: a blocking AskUser tool with structured options and a free-text escape. Anthropic reports this worked after two failed attempts (extra parameters on the plan tool, then a custom markdown output format) [S6].
  • Tasks: a small task tool with pending / in_progress / completed, optional dependencies and the ability to edit or delete tasks. Anthropic moved from rigid to-dos with reminders to tasks because newer models took reminders as a rule to follow the list literally [S6].

6.7 Verification

The "verify" half of the loop is where quality comes from:

  1. Diagnostics after edit (LSP if present, else syntax check). Surface only new errors.
  2. Project commands from MINIMAKE.md or config: lint_cmd, test_cmd, build_cmd. Aider's lint-and-test auto-fix loop is the model: failures go back to the model until they pass or it reports what it could not fix [S12].
  3. Completion check: before the final message the model must list what it verified and what it did not. A Stop hook can enforce this.
  4. Independent review (optional, v2): run your reviewer role on the diff before the user accepts it.

6.9 Streaming and interrupts

  • Stream text and tool progress token by token.
  • Esc cancels the running tool and waits; typing a message queues it and the model reads it after the current tool finishes (Claude Code behavior [S2]).
  • Cancel must kill the process group on the user's machine and set the Redis cancel flag so the backend stops calling the model [M].

6.10 Replay and debugging

Because every model call and tool result is an event, any run can be replayed offline against the same inputs, and a bad run can be turned into an eval case with one command. OpenHands credits its append-only event log and immutable configuration for deterministic replay and easy debugging [S20]. [P] Store the exact prompt and tool schemas hash with each model call.

7. Tools

7.1 Design rules (from Anthropic's tool team) [R:S6, S7]

  1. A small, deliberate set. Claude Code has about 20 tools and treats each new one as a cost, because each is another option for the model to think about [S6].
  2. Shape tools to what the model is good at. Watch transcripts, remove tools it fights with, and add structure where free text failed (the AskUser tool) [S6].
  3. Let the model find its own context. A Grep tool beat pre-indexed retrieval in their experience because the model could build context itself [S6]. Keep an optional index as an experiment [S31].
  4. Add capability through progressive disclosure, not new tools. Skills and subagents extend what the agent can do without enlarging the tool list [S6].
  5. No examples in tool descriptions for the newest models; use expressive parameters instead [S7].
  6. Defer rarely used tools behind a tool-search mechanism so idle MCP tools cost almost nothing [S1].

8. Permissions, sandbox and security

This section decides whether MiniMake is safe to ship. Everything here is enforced on the user's machine.

8.1 The threat model in one picture

Simon Willison's "lethal trifecta" names the dangerous combination: private data, untrusted content, and a way to communicate externally. An agent that has all three can be tricked by instructions hidden in content it reads [R:S29]. Coding agents are useful precisely because they have all three (they read your code, read web pages and issues, and run commands), so the job is to reduce blast radius, not to hope the model resists [S29].

Where untrusted text can enter MiniMake: web pages and search results, files in cloned repos, issue and PR text, dependency READMEs, MCP tool descriptions and responses, command output, skills and plugins [S29]. The security community's consensus in 2026 is that prompt injection is not solved; the effective defenses are architectural: least privilege, allowlists, sandboxing, human approval for risky actions, and removing one leg of the trifecta [S29].

Attack Example Primary defense
Indirect prompt injection A README tells the agent to upload ~/.ssh Sandbox (no network, no home access) + egress allowlist + taint-tightened approvals
Tool poisoning A malicious MCP server hides instructions in a tool description Trust levels per server; review descriptions; no auto-approve for new servers
Supply chain via skills/plugins A marketplace skill exfiltrates credentials No marketplace in v1; signed, scanned skills later (§10.6)
Self-modification Agent edits its own hooks or config to disable checks Protected paths read-only; config changes require approval
Credential theft Model reads env vars or .env Sanitized env; read-deny on secret paths; redaction
Backend compromise Attacker makes the backend send "approved" Local policy is final; hard denies cannot be overridden remotely
Rogue device Stolen shared token registers as another user's daemon Per-device credentials bound to user; revocation
Runaway cost Loop burns tokens Step, dollar and failure limits

8.3 Rules

Rule syntax [P], modeled on Claude Code's allow/ask/deny rules [S1]:

# .minimake/settings.toml  (project)   ~/.minimake/settings.toml (user)   /etc/minimake/managed.toml (org)
[permissions]
allow = [
  "bash(npm test)",
  "bash(git status)",
  "bash(git diff:*)",
  "edit_file(src/**)",
  "web_fetch(domain:docs.python.org)",
]
ask = [
  "bash(git push:*)",
  "bash(npm install:*)",
]
deny = [
  "read_file(.env*)",
  "read_file(~/.ssh/**)",
  "bash(curl:*)",
  "bash(rm -rf:*)",
]
  • Evaluation order: deny, then ask, then allow; managed settings override user, which override project (Claude Code layering [S1]).
  • Exact strings first. Saved approvals are the exact command the user approved, not a pattern the model proposed. No blanket "always allow".
  • Parse compound commands. a && b | c must be split and each part checked; otherwise allow bash(ls) lets ls && curl evil through. [P] Use a real shell parser; unknown syntax falls back to "ask".
  • Project-level rules and hooks require a trust prompt the first time a folder is opened, like Gemini CLI's trusted folders [S15].

8.4 Sandbox

OS Mechanism Notes
macOS Seatbelt (sandbox-exec) profiles Codex and Claude Code use this [S9, S3]
Linux bubblewrap for filesystem; Landlock + seccomp as alternative Claude Code uses bubblewrap [S3]; Codex uses Landlock/seccomp [S9, S10]. Landlock may not work inside containers without the right host support [S9]
Windows WSL2 first; native later Claude Code's sandbox requires WSL2 [S3]

Policy [P] (matching what Codex and Claude Code do by default [S9, S3, S10]):

  • Writable: the project directory and a temp dir. Read-only inside it: .git/, .minimake/, shell rc files. Codex keeps .git and .codex read-only even in workspace-write [S10].
  • Readable: the project, system directories needed for toolchains. Denied: home directory secrets (~/.ssh, ~/.aws, browser profiles, keychains).
  • Network: off by default for sandboxed commands; allowed through a local proxy with a domain allowlist; the first time a command needs a new domain the user is prompted [S3].
  • Both filesystem and network isolation are required. Without filesystem isolation a compromised agent can alter system files to gain network access, and without network isolation it can leak files [S3].
  • Auto-allow variant: commands that run fully inside the sandbox can skip prompts; commands that need to escape (new domain, outside paths) fall back to the normal permission flow [S3].
  • Escape hatch: a retry "outside the sandbox" must go through full approval and be logged separately [S3].

8.5 Environment and secrets

  • Start the shell with a sanitized environment: strip variables matching *KEY*, *TOKEN*, *SECRET*, *PASSWORD*, cloud credentials; allow named exceptions per project.
  • Two-form denylist (from your CLI plan [M]): a human-readable list in settings and a hard-coded list in the read tools that refuses .env*, private keys, credential stores. The hard-coded form cannot be edited by the model or by a project file.
  • Redaction filter on every tool result before it leaves the machine: pattern-based secret detection (cloud keys, JWTs, private-key blocks, high-entropy strings near words like "key"). Your rulebook already makes secret and PII redaction mandatory before external model calls [M].
  • Git credentials are used through the OS credential helper so git push works without the model seeing the token. Managed Agents does the equivalent by wiring the token into the git remote at setup so the agent never handles it [S5].
  • MCP OAuth tokens live in the OS keychain; MiniMake calls MCP servers through a local proxy so the model sees results, not credentials (the vault-plus-proxy pattern from Managed Agents [S5]).

8.6 Taint tracking (a differentiator) [P]

Each session carries tainted: bool. It becomes true when untrusted content (trust: external) enters the context. While tainted:

  • Any tool that can move data out (network, git push, MCP write tools, email-like tools) requires human approval even in accept-edits or auto mode.
  • Writes outside the project are denied.
  • The UI shows a visible "tainted" marker with the reason, and the user can clear it only by starting a fresh context or explicitly accepting the risk.

This follows the pattern recommended for MCP-heavy setups: egress goes through an allowlist and tainted sessions need a human gate [S29]. It is rare in shipping products, which makes it a credible security feature to market.

8.7 Auto mode classifier

  • A separate small model reviews proposed actions with a policy prompt and returns allow / block / ask. Claude Code's classifier blocks actions that escalate beyond the request, target unrecognized infrastructure, or appear driven by hostile content the agent read [S3, S4].
  • MiniMake rules [P]: (1) the classifier only runs on calls that survived the local deny rules; (2) it can only move a call from "ask" to "allow", never override a deny; (3) it never sees secrets; (4) every verdict is logged; (5) ship it only after an eval of at least a few hundred labeled tool calls including injection attempts, and report false-allow rate as a release gate.
  • The verdict comes from your backend, so a compromised backend could always say "allow"; that is why the sandbox and hard denies remain the real protection.

8.8 Hooks as deterministic guardrails

Hooks run a script or HTTP call at lifecycle events and can block. In Claude Code, PreToolUse exit code 2 blocks the call and shows the reason to the model; Stop exit code 2 forces the agent to continue; four handler types exist (command, http, prompt, agent) [S34]. The docs state the principle plainly: a CLAUDE.md instruction is a request; a hook is enforcement [S1].

MiniMake events [P]: SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, SubagentStart/Stop, PreCompact, Stop, SessionEnd. Exit 0 allows, 2 blocks. Project hooks need the folder-trust prompt. Hooks run outside the model's context and cost nothing unless they return text [S1].

8.9 Device identity and the backend link

Fixing the weakness found in the current daemon [M] (one shared pairing token; WebSocket path takes the workspace from the URL):

  1. Pair with device-code flow: minimake login shows a short code; the user approves in the web app; the CLI receives a long-lived device credential stored in the OS keychain.
  2. Per-connection short-lived token (JWT) signed by the backend, containing user ID, device ID and expiry; verified on connect.
  3. Server verifies ownership of any workspace or project the device asks to touch.
  4. Revocation list checked on connect and on a heartbeat; a "sign out all devices" button.
  5. TLS only; pin the backend certificate or use a trusted CA bundle.

8.10 Audit, kill switch and transparency

  • Audit log of every proposal, decision (who or what decided), tool result summary and hook outcome, kept locally and sent to the backend log. Your audit_log utility already exists [M].
  • Kill switch: Ctrl+C twice, a minimake stop command, and a web button that sets the cancel flag.
  • Always show the exact command before it runs, the files an edit touches, and the current mode, sandbox status and taint state in the status line.

8.11 Enterprise controls (v3) [S4, S15]

Managed settings that users cannot override (permission rules, allowed MCP servers, sandbox policy, model allowlist, disabled bypass mode), policy files like Gemini CLI's Policy Engine, and OpenTelemetry export of usage and events [S15, S4].

9. Context, memory and instructions

9.1 What goes into the context window

Order matters for caching: stable things first, changing things last.

  1. System prompt (short; product and role only) [S7].
  2. Tool schemas (core tools full; deferred tools as names only) [S1].
  3. Instruction files: global ~/.minimake/MINIMAKE.md, repo MINIMAKE.md, subdirectory files as the agent enters them, plus AGENTS.md / CLAUDE.md if present. Claude Code loads all levels additively and loads subdirectory files as it works in them; keep each under about 200 lines [S1].
  4. Rules matched to files currently in play (path-scoped) [S1].
  5. Auto-memory index (first ~200 lines or 25 KB) [S2].
  6. MiniMe project context if the project is linked: instructions, plan, parts and wiring summaries, wireframe summaries [M].
  7. Conversation history (compacted when needed).
  8. Tool results (older ones cleared first on pressure) [S2].

9.2 Instruction file spec

MINIMAKE.md is plain Markdown. Guidance from Anthropic's team: keep it light, describe what the repo is for, spend tokens on gotchas the model cannot see from the file tree, and avoid stating obvious things; use references to skills for procedures such as how to verify work [S7].

# Project: soil-monitor

- `config.h` is generated by `make config`; never edit it by hand.

## Commands
- test: `pytest -q`
- build: `make build`
- lint: `ruff check .`

## Verification

9.4 Compaction

  • When context nears the limit, clear old tool outputs first, then summarize the conversation; keep user requests and key code snippets [S2].
  • Let users add "compact instructions" (what to keep) in MINIMAKE.md or pass a focus to /compact [S2].
  • Stop auto-compacting after repeated failures where one huge output refills the window, and show an error with recovery steps [S2].
  • Because the full session log is stored outside the context, nothing is lost when compaction drops messages; the harness can re-fetch positional slices of the log if the model needs earlier detail [S5].

9.5 Retrieval strategy

  1. Default: grep, glob, read with the model driving [S6].
  2. v2: repo map (tree-sitter outline ranked by relevance) as a cheap orientation block, as Aider does with PageRank over symbol references [S12].
  3. v3, only if your own eval shows a gain: local semantic index. Evidence is mixed: Anthropic's team chose grep [S6], while May–July 2026 tests and Augment's vendor benchmark favored indexes [S31]. Roo Code lets users pick their own embedding provider and vector store, which is a good model if you add one [S19].

10. Extensibility

10.1 Skills (open standard)

A skill is a folder with SKILL.md (YAML frontmatter with at least name and description, then instructions) and optional scripts/, references/, assets/. Agents load only name and description at startup, the body when a task matches, and bundled files only when referenced [R:S28]. The format was created by Anthropic, released openly and adopted by Claude Code, Codex, Cursor, Gemini CLI, OpenClaw and others [S28]; Zed supports it too, with a disable-model-invocation flag and a recommended body under 500 lines [S27].

MiniMake [P]: read skills from ~/.minimake/skills, <repo>/.minimake/skills, and (with a trust prompt) <repo>/.agents/skills and .claude/skills so users bring existing skills; support disable-model-invocation: true for skills with side effects; ship a few built-in skills (verify, review, create-skill, init); allow a skill to run in an isolated subagent context.

10.2 Slash commands

10.5 MCP

  • Client: stdio and Streamable HTTP. The 2026-07-28 spec removes protocol-level sessions and the session-ID header, moves long-running work into an official tasks extension (server returns a task handle; client polls tasks/get and can send input via tasks/update), deprecates dynamic client registration in favor of Client ID Metadata Documents, tightens OAuth (issuer binding, OAuth 2.1/OIDC), and adds a formal deprecation lifecycle with at least a twelve-month window [R:S26]. [P] Build against this spec and keep a compatibility shim for older servers.
  • Trust levels per server: trusted (first-party or reviewed), ask (default), blocked. Tool descriptions from non-trusted servers are shown to the user at install, and their responses taint the session.
  • Cline's lesson: MCP is often the real security answer; a careful local agent becomes risky when every user installs unreviewed servers with broad auto-approve. Keep autoApprove empty for write, delete, network and payment-adjacent tools [S13].
  • Tool search: defer schemas so ten servers do not cost thousands of tokens each turn [S1].

10.6 Plugins and marketplace (later)

Plugins bundle skills, subagents, hooks and MCP definitions into a versioned installable unit, namespaced (/plugin:skill) to avoid collisions [S1]. Do not open a public marketplace until you can scan and sign submissions. The OpenClaw ecosystem is the cautionary example: one analysis cited by its community found over a third of marketplace skills had security flaws and hundreds leaked credentials, and a security team demonstrated a malicious third-party skill that exfiltrated data without the user noticing [S21]. [P] Order of trust: built-in → your curated first-party → verified publishers (signed, scanned, permission manifest) → community (off by default).

11. Workflows

11.1 Checkpoints and rewind

  • Before every file edit, snapshot the affected files locally (content-addressed store under ~/.minimake/checkpoints/<run_id>/).
  • Rewind (Esc Esc or /rewind) restores files to an earlier step and optionally rewinds the conversation. Claude Code works this way: checkpoints are separate from git, survive resume, cover only file changes, and skip symlinked and hard-linked files [S2].
  • Be honest in the UI: actions on remote systems (databases, APIs, deployments) cannot be checkpointed and rely on permissions instead [S2].
  • Replit's checkpoints also capture conversation context and connected databases [S32]; for MiniMake, file plus conversation is enough.
  • Gemini CLI checkpoints before destructive actions and offers /restore [S15].

11.2 Sessions

  • Sessions are stored locally and in the backend log. minimake --resume reopens the same session ID; --fork copies history into a new ID [S2].
  • Same session open in two terminals: warn and offer to fork.
  • Sessions are tied to a directory; branches change the files but not the conversation [S2].

11.3 Git integration

  • Read git state (branch, dirty files, recent commits) into context [S2].
  • Never commit, push, rebase or reset without approval; treat them as R2/R3.
  • Optional auto-commit per change (off by default; Aider commits every AI edit with a generated message, which is clean for history but noisy for squash-merge teams [S12]).
  • Optional "AI authored" trailer on commits the agent makes.

11.4 Parallel work with worktrees

  • minimake --worktree feature-x creates a git worktree and a session bound to it; up to N parallel sessions per user by plan.
  • Cursor runs up to eight parallel agents on worktrees or cloud machines [S16]; Claude Code recommends worktrees for parallel sessions [S2]; Gemini and Cline list worktrees as a feature [S15, S13].
  • A "compare runs" view (v3) shows diffs from several agents on one task, the idea behind Copilot Agent HQ's side-by-side PRs [S30]. It multiplies cost, so keep it opt-in.

11.5 Headless and CI

  • minimake -p "task" runs once, prints the result and exits; --output-format json for scripts (Claude Code, Gemini and Cline have equivalents [S2, S15, S13]).
  • A GitHub Action / CI wrapper for PR review and fix-the-failing-check tasks. Claude Code and Amp have review bots [S1, S31].
  • Headless runs use bypass-free policies: explicit allow rules only, no prompts; anything not allowed fails the run.

11.6 Lint, test and build loops

Configure once in MINIMAKE.md or settings:

[verify]
lint  = "ruff check ."
test  = "pytest -q"
build = "make build"
after_edit = ["lint"]        # run after each edit batch
before_finish = ["test"]     # Stop hook blocks until this passes
max_fix_attempts = 3

11.7 Review before accept (MiniMe-specific) [M][P]

/review runs your reviewer role on the current diff; /security-review runs the security reviewer plus dependency and secret scans. Output is a short list of findings with file and line, which the user can send back to the agent as tasks. Devin Review and BugBot show how popular this is: Devin Review organizes large diffs, detects copied or moved code, flags likely bugs and can trigger autofixes [S17, S16]. Because you already have reviewer roles and a security aggregator, this is MiniMake's strongest differentiator and costs little to build.

11.8 Spec-driven mode (later) [S18]

Kiro's three files are a useful pattern: requirements.md (user stories with acceptance criteria in EARS notation), design.md (architecture, data models, interfaces), tasks.md (sequenced tasks linked to requirements) [S18]. [P] Reuse MiniMe's Plan tab outputs as these files when a project is linked. Offer both Feature specs and Bugfix specs. Keep it optional; some users want to just chat.

11.9 Browser ↔ MiniMake handoff and remote control

The recommended design (see also earlier discussion): explicit pull and push on your existing version table, with a "checked out in MiniMake" banner in the browser, not live two-way sync.

  • Pull: minimake pull <project> writes the cloud project to a folder, skipping junk (node_modules, .git, build output).
  • Checked out: browser code files become read-only with a banner and a "release checkout" button.
  • Push: minimake push sends changed files; each becomes a new version in history; push carries the version it pulled from and is rejected if the cloud moved on.
  • Remote control (v2): the web app shows a live run (messages, diffs, approvals) from the backend session log and can approve or cancel. Claude Code's Remote Control runs the session on your machine and drives it from a browser while files stay local [S2]. Approvals made remotely still pass the local hard deny rules.
  • Git later: an optional GitHub link where push also creates a branch. Claude Code's cloud/teleport flow uses a pushed branch as the handoff and, for non-GitHub repos, bundles the local repo (up to 100 MB) [S2].

11.10 Scheduled and background runs

Reserved for MiniMate (see minimate_guide.md). MiniMake v1 supports background shells and headless runs, but no unattended agent runs.

  • Events are never updated or deleted except by retention policy. This also makes the table cheap to reason about for audits.
  • Hot state (cancel flag, budgets, current approval waiters) in Redis, as today [M]; cold truth in Postgres.
  • Retention: default 90 days of events, shorter on the free-adjacent plans; user-visible delete.
  • Privacy: tool results may contain code and secrets; encrypt at rest, restrict access to the owner, and list sub-processors per your rulebook's privacy section [M].

13.4 Workers and scaling

  • Stateless workers execute loop steps; a run's state is rows plus Redis. Any worker can continue any run, the "cattle not pets" principle [S5].
  • Your current setup has one uvicorn process and a small agent task pool [M]. For MiniMake, run N workers behind a queue; keep WebSocket connections on a dedicated gateway process that forwards events to workers via Redis pub/sub.
  • Pending approvals and daemon futures currently live in process memory and expire after 15 minutes [M]; move them to Redis or the database so restarts and multiple workers work.
  • Backpressure: per-user concurrent run limit; per-plan queue priority.

13.5 Failure modes to handle explicitly

Failure Behavior
Client disconnects mid-tool Mark call failed: disconnected; run → paused_disconnected; on resume the model is told which call failed
Worker dies mid-model-call Another worker replays from last event; idempotency key on model calls to avoid double billing
Provider outage Fall through chain; if none, paused_error with provider status text
Duplicate tool result Ignore by call_id

14. Models, metering and economics

All price figures below come from your Financial Strategy Rulebook v1.1 [M]. Cached-input prices for some models are [A]. Replace everything marked [A] with measurements from your instrumentation before setting prices.

14.1 What the benchmarks imply for model choice

Terminal-Bench 2.1 (leaderboard snapshot) reports GPT-5.6 Luna at 75.7% and Claude Sonnet 5 at 74.6%, GPT-5.6 Terra at 78.4%, Claude Opus 4.8 at 78.9%, GPT-5.5 at 83.1%, Fable 5 at 83.8%, and GPT-6 Astra at 87.4% [S25]. Differences in harness and reasoning-effort settings mean these are not apples to apples, but the price gap between Luna and Sonnet/Opus-class models is large. If Luna-class models hold up in your own eval, MiniMake's main loop can run on a cheap class with escalation, which changes the economics completely.

A separate harness-cost test showed that for the same accuracy one harness cost 2x more GPU time than another on self-hosted models [S25]. Token-efficient context handling is therefore a margin lever, not just a nicety.

14.3 Cost per session (illustration) [A]

Assumed session: 40 steps, average 30K input tokens per step (85% served from cache), 600 output tokens per step. That is 1.2M input tokens (1.02M cached, 0.18M uncached) and 24K output tokens.

So the same session can cost 40x more depending on the model. This is why routing and escalation are the main economic design.

14.4 Metering: why raw tokens break

Your rulebook counts cached input tokens fully in the user-facing meter [M]. That session counts about 1.2M tokens, which would use 30% of Basic's 4M Standard pool in one session and all of Moderate's 1.2M Advanced pool. Options [P]:

Option How Pros Cons
A. Separate MiniMake pool, cached reads at a discount weight (e.g., 10%) Count 0.18M + 0.1×1.02M + 0.024M ≈ 0.31M per session Familiar token unit; honest Still confusing to users
B. Agent credits Credit = estimated cost weighted by model class; show "sessions left" One simple number; follows real cost You must publish the conversion
C. Per-run ceilings only Cap dollars per run, monthly session count per plan Simple to explain Does not protect margin on heavy users

Recommendation [P]: option B for display, A internally, with C as a safety net. Show the user "about N sessions left this month" and the estimated cost range before a long run.

14.5 Pricing method (no numbers, on purpose)

Apply your own rule: price ≥ COGS at the cap ÷ 0.45 [M]. Steps: (1) decide the monthly credit pool per plan; (2) compute COGS if a user burns the entire pool on the plan's default chain; (3) divide by 0.45; (4) check against competitor price points [S16, S25: Claude Code Pro $20, Codex included with ChatGPT plans, Cursor Pro $20 with metered spend] and your Bangladesh and global price rungs [M].

Example only [A]: if a pool is 60 Luna-class sessions (≈ $5.40 COGS) plus 3 escalated Sonnet-class sessions (≈ $2.40), COGS at cap ≈ $7.80, so the floor price is ≈ $17.30 per month before payment fees. Do not copy this; measure first.

14.6 Cost controls

  • Prompt caching everywhere, with a stable prefix and append-only history. Never rewrite earlier messages.
  • Clear old tool outputs before summarizing [S2].
  • Cheap classes for summaries, titles, classifier, compaction.
  • Subagents keep exploration out of the main context, so they usually save tokens [S1].
  • Architect/editor split where a strong model plans and a cheap one edits [S12].
  • Batch/Flex pricing for non-interactive runs (CI review, scheduled tasks) where your rulebook already uses half-price batch for Brain jobs [M].
  • Per-run dollar ceiling with a "grant more" action [M].
  • Telemetry first. Log tokens, cache-hit rate, steps and cost for every run so you can tune with data (Roadmap Tech-A) [M].

14.7 Free tier

Do not offer free MiniMake usage on production keys. Your rulebook forbids free-tier keys in production, and shell access plus agent loops are the easiest way to abuse a free plan [M]. If you want a demo, offer a tiny capped trial per verified user.

Appendix G — Glossary

Harness: the code around the model (loop, tools, context, safety). Hands: where tools execute. Brain: model plus loop. Session log: append-only event record of a run. Taint: marker that untrusted content has entered the context. ACP: Agent Client Protocol (editor↔agent). MCP: Model Context Protocol (agent↔tools). Skill: a folder of instructions loaded on demand. Checkpoint: local file snapshot before an edit. Worktree: a separate git working directory for a branch.
